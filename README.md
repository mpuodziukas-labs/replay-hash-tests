# replay-hash-tests

Proves: a seeded pipeline replays bit-for-bit identically across two independent processes, checked by hashing every output. Verify in 60s: `python3 replay.py`

A clone-and-run demonstration of **deterministic replay testing**: generate a seeded synthetic corpus of **47,312** records, run each through a deterministic transformation pipeline, SHA-256 every record together with its output, and compare two independent runs position by position (divergence = 0).

```
47,312 deterministic replays | 0 divergence | corpus_hash=3e806db2c4978dfae932b98d3d2dfbcbc76cd4f48f5b29b6181be9eb531167a8
```

## Business problem

A pipeline that is supposed to give the same answer every time can quietly drift: a clock read, a float, an unordered set, a changed rule. This repo shows how to catch that drift before customers or money are hit, by hashing every output and failing when two runs of the same input differ by even one bit.

## Run it in 60 seconds

```bash
python3 replay.py
```

Expected output, which is the only line printed on success:

```
47,312 deterministic replays | 0 divergence | corpus_hash=3e806db2c4978dfae932b98d3d2dfbcbc76cd4f48f5b29b6181be9eb531167a8
```

The 60 second bound is asserted, not assumed: `tests/test_hostile.py::test_cli_wall_time_under_60s` fails if `python3 replay.py` takes 60 seconds or more. To see the time yourself, run `time python3 replay.py`.

Tests and mutation check:

```bash
pip install -r requirements.txt
python3 -m pytest -q
python3 mutants.py
```

`mutants.py` breaks `replay.py` in 6 known ways, on a temporary copy, and requires the test suite to fail each time. It exits 0 only if the control run passes and all 6 mutants are killed.

## Interface

`python3 replay.py` takes no arguments. Exit codes: `0` = all checks held and the line above was written to stdout; `1` = a check failed (reasons on stderr); `2` = arguments were given. The harness fails if the corpus is not 47,312 records, if the two runs diverge, if the corpus hash is not the pinned value, or if it cannot write its result line. These are plain `if` statements, so `python -O` cannot skip them.

## How it works

| Stage | What it does | Why it is deterministic |
|-------|--------------|-------------------------|
| Corpus generation | `generate_case(i, seed)` derives each record from `(index, seed)` via SplitMix64 | Pure integer arithmetic; no `random` global state, no clock, no I/O |
| Transformation | `transform(case)` runs a normalize, enrich, score pipeline | Fixed-weight integer model, no floating-point nondeterminism |
| Hashing | `hash_record()` SHA-256s each input record together with its output, in a type-tagged canonical encoding | Stable bytes; an int is never a str, a tuple is never a list, NaN and Infinity are refused |
| Verification | Replay A runs in-process; replay B runs in a separate process with a different `PYTHONHASHSEED` and `TZ`; compared position by position | `count_divergences()` must return 0; corpus roots must match |

The corpus root hash (`corpus_hash`) is a SHA-256 over the ordered list of per-record hashes: one fingerprint for the whole corpus. Because each per-record hash covers the input as well as the output, editing a generated input moves the root even when the transform would discard the edit. Empty runs are refused.

## What this is and is not

- It is a runnable proof that a seeded pipeline produces identical, hash-verified output across independent runs.
- It is not a production deployment, not a log of a real workload, and not built from any external data. The corpus is generated from the fixed seed `0xC0FFEE` by `replay.py`.

## Reproducibility notes

- Seed: `0xC0FFEE` (pinned in `replay.py`).
- The pipeline is integer-only with canonical serialization, designed to give the same corpus hash on any platform. CI runs the harness and tests on CPython 3.9 to 3.12 on Linux only, so other operating systems are untested here.
- Tamper-evidence: `replay.py`, `REFERENCE` and the tests pin the expected corpus hash. A change that re-pins the hash in the same pull request is caught by `check_reference.py`, run in CI against the value on the base branch: it fails unless a commit message carries a `REFERENCE-CHANGE:` line.

## Honesty Statement

- The corpus is synthetic. Every record is generated by `replay.py` from the fixed seed; there is no external data source and no real data.
- This demonstrates a method on a small pure pipeline. It is not a measurement of any real workload.
- Every number in this README is printed by `python3 replay.py` or asserted in the tests: 47,312 records, 0 divergence and the corpus hash.
- "Hash-verified" means the SHA-256 values match across two runs here and match the value pinned in the tests. It is not an external audit.

## Limitations

- The corpus is synthetic. It shows the property of deterministic replay, not the behavior of any specific production system.
- "Determinism" here means reproducibility of a pure pipeline, not a claim about any nondeterministic component such as a model, a network service or a concurrent system.
- Cross-platform identity relies on the pipeline being integer-only and using canonical serialization. Floating-point math, set or dict ordering dependence, or locale-sensitive formatting could break it. This repo avoids all of those.
- State kept inside one process, such as a module-level cache, repeats in every replay inside it. The second replay runs in its own process, so such state no longer hides, but the test varies hash seed and time zone on one machine only.
- The harness does not exercise distributed or concurrent replay.
- The pin check is a speed bump, not a lock. A pull request author can add a `REFERENCE-CHANGE:` line, and anyone with write access to the base branch can move `REFERENCE` outright. The line makes a re-pin visible to a reviewer; it does not make it impossible.
- The second replay runs on the same machine. It differs in hash seed and time zone only, not in operating system or Python build.
